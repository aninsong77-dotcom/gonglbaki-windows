# 진단 기록 분석 — 한글 조합창 오류 (1차)

분석일 2026-08-16 · 대상 `C:\Users\안인성\gongulbaki_ime_debug.txt` (323건)
분석 방식 = 읽기 전용 집계. 코드·파일 변경 없음.

## 결론 먼저

**버그가 터진 순간은 잡히지 않았다.** 진단 코드는 정상 작동했으나,
기록이 남은 이틀(8/6·8/13) 동안 축어록 편집에서 증상이 재현되지 않았다.

## 기록 현황

| 날짜 | 건수 | 내용 |
|---|---|---|
| 2026-08-06 | 316 | 축어록 편집 작업 (한글 조합 157 + 편집 중 Esc 159) |
| 2026-08-13 | 7 | 입력칸(INPUT) 타이핑 7초간 |

진단 코드는 8/6에 설치되어 8/13까지 살아 있었으나, **앱을 실제로 쓴 날이 이틀뿐**이다.

## 발견 1 — 축어록 편집에서는 이상이 한 건도 없었다

8/6의 한글 조합 시작 157건 전부에서 커서 좌표를 정상적으로 구했다.

```
caretRects 가 1 이상 : 157
caretRects 가 0      : 0
```

`caretRects`가 0이면 화면 엔진이 커서 위치를 못 구한 것이고, 그때 조합창이 좌상단으로 떨어진다.
157건 모두 정상이었으므로 **그날 축어록 본문 편집에서는 증상이 없었다.**

## 발견 2 — Esc가 조합을 깨뜨린 증거는 없다

편집 중 Esc가 159번 눌렸다. Esc는 재생·정지 단축키이자 한글 조합을 취소하는 키라
유력한 용의자였으나, **159건 전부 조합 중이 아닌 상태에서 눌렸다.**

```
Esc 누를 때 조합 중(isComposing:true)  : 0
Esc 누를 때 조합 중 아님               : 159
```

현재 기록만으로는 Esc를 원인으로 볼 수 없다. 다만 재현 사례가 없어 **배제된 것은 아니다.**

## 발견 3 — 8/13의 7건은 오탐일 가능성이 높다

7건 모두 동일 패턴이다.

```
tag: "INPUT", editable: false, lineId: null
caret: { anchorType: "DIV", caretRects: 0, caretAt: null }
inDialog: false, activeIsTarget: true
rect: { x:473, y:432, w:334 }   ← 화면 중앙의 폭 334px 입력칸
keyCode: 84(ㅅ) 8(←) 48(0) 13(Enter) 8(←) 84(ㅅ) 51(3)
```

**판단 근거**: 진단 코드의 커서 확인은 `window.getSelection()` 을 쓴다.
그런데 `<input>` 안의 커서는 Selection API로 읽히지 않는 것이 크로미움의 정상 동작이다.
기록의 `anchorType: "DIV"` 가 그 증거다 — 선택 영역이 입력칸 안이 아니라 바깥 DIV를 가리키고 있다.
즉 **입력칸에서는 `caretRects: 0` 이 정상값**이며, 이상 신호로 볼 수 없다.

`keydown` 감시가 `INPUT` · `TEXTAREA` 까지 대상에 넣은 것이 오탐의 원인이다.

**단, 확정은 아니다.** 그 7초 동안 사용자가 실제로 증상을 겪었을 가능성은 남아 있다
(같은 시각대에 조합 시작 기록이 하나도 없다 = 한글 조합이 아예 시작되지 않았을 수도 있다).
사용자 확인이 필요하다.
