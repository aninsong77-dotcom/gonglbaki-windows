## 0. 먼저, 온디바이스(외부 전송 없음)는 지켜지고 있는가

**[확인] 지켜지고 있다.** 음성·축어록을 외부로 보내는 코드는 하나도 없다.

- 화면 코드에서 외부 주소를 호출하는 곳 없음. 등장하는 외부 주소 5개는 전부 **설정창의 기부처 안내 링크**로,
  사용자가 직접 클릭해야 열리는 링크다(자동 통신 아님).
- 변환·분석 요청은 전부 `http://127.0.0.1:5577` — 즉 **자기 컴퓨터 자신**을 가리키는 주소다.
- 로컬 서버도 `app.run(host="127.0.0.1", ...)` 로 떠 있어(`server/app.py:2056`)
  **같은 네트워크의 다른 기기에서는 접속할 수 없다.** (`0.0.0.0` 이었다면 공유기에 물린 다른 기기에서
  접근 가능했을 텐데, 그렇지 않다.)

즉 "인터넷 서버로 상담 내용이 나간다"는 걱정은 코드상 근거가 없다. 다만 아래 보안 항목은 성격이 다른 문제다.

## 1. 보안 — 조치가 필요한 항목

### 🔴 S1. 외부 웹사이트가 앱 내부 창으로 열린다 (심각) — ✅ 2026-08-06 수정 완료

**[확인]** `electron-main.cjs` 의 `setWindowOpenHandler` 가 **주소를 가리지 않고 전부 `action: "allow"`** 로
처리한다. 그래서 설정창의 기부처 링크(네이버·유니세프 등)를 누르면 그 사이트가 **사용자의 기본 브라우저가
아니라 곤글박이 앱 안의 새 창**으로 열린다.

문제는 이렇게 열린 창이 부모 창의 설정을 물려받아 **`preload.cjs` 가 노출한 기능을 그대로 쓸 수 있다**는 점이다.
`preload.cjs` 는 사례서랍용으로 다음을 열어두고 있다:

- `readText` / `readBinary` — **임의 경로의 파일 읽기**
- `writeText` — **임의 경로에 파일 쓰기**
- `openExternal` — 임의 파일 실행/열기

즉 이론상, 그 외부 사이트가 (해킹·중간자 공격 등으로) 악성 스크립트를 내려주면
**사용자 PC의 파일을 읽거나 쓸 수 있는 통로**가 된다. 상담 축어록이 담긴 폴더까지 닿을 수 있는 권한이다.

**권장 조치**: 외부 주소(http/https 로 시작하는 남의 사이트)는 앱 창에서 열지 말고
`shell.openExternal()` 로 **사용자의 기본 브라우저에서 열고, 앱 창 생성은 거부(`deny`)** 한다.
앱 내부 창은 `127.0.0.1` 의 도움말(help.html)만 허용한다. 사용자가 느끼는 동작은 거의 같다
(링크가 크롬/엣지에서 열림). 수정 범위가 작고 부작용이 거의 없다.

### 🟠 S2. 로컬 API 가 아무 웹사이트에나 열려 있다 (중간)

**[확인]** `server/app.py:175` 에서 `CORS(app, resources={r"/api/*": {"origins": "*"}})` —
**모든 출처 허용**이다. 서버가 `127.0.0.1` 에만 떠 있어 다른 기기에서는 못 붙지만,
**사용자가 크롬으로 아무 웹사이트나 열어둔 상태에서 곤글박이가 켜져 있으면, 그 웹사이트의 스크립트가
`http://127.0.0.1:5577/api/...` 를 호출할 수 있다.**

실제로 호출 가능한 것 중 위험한 것:

| 엔드포인트 | 무엇이 가능한가 |
|---|---|
| `POST /api/file/hwpx-preview` | **[확인]** 경로만 주면 그 hwpx 파일 내용을 읽어서 돌려준다. 경로 검증이 "`.hwpx` 로 끝나는가" 뿐이라, 경로를 아는 한 임의 파일 읽기 |
| `POST /api/report/observer` | **[확인]** `out_path` 로 받은 **임의 경로에 파일을 쓴다** |
| `GET /api/debug-log` | **[확인]** 디버그 로그 전문을 반환. 다만 로그 자체는 아래 P1 을 빼면 깨끗하다 |
| `DELETE /api/models/delete/<name>` | **[확인]** 받아둔 변환 모델 삭제 가능(데이터 손실은 아니나 사용자 피해) |

**[추정]** 실제 공격이 성립하려면 사용자가 악성 사이트를 방문해야 하고, 파일 경로도 알아야 해서
현실적 위험은 "당장 위급"보다는 "구조적으로 열어둘 이유가 없는 문"에 가깝다. 다만 상담 자료를 다루는
프로그램의 성격상 닫는 게 맞다.

**권장 조치**: ① CORS 를 `origins: "*"` 대신 앱 자신(`http://127.0.0.1:5577`)만 허용,
② 파일 경로를 받는 엔드포인트는 사례서랍 루트 폴더 안쪽인지 검사, ③ `/api/debug-log` 는 유지하되
파일명 마스킹 검토.

### 🟢 프라이버시 설계는 대체로 잘 돼 있다 (확인 결과)

**[확인]** 걱정되는 부분을 일부러 찾아봤는데, 오히려 잘 만들어져 있었다:

- **상담 내용(변환된 텍스트)은 로그에 절대 안 남는다.** 분석 요청도 `"단어 정리 요청 (12345자)"` 처럼
  **글자 수만** 기록한다.
- **음성 파일명도 안 남긴다.** 변환 시작 로그는 `파일: .mp3` 처럼 **확장자만** 남긴다
  (`server/app.py:1167`). 파일명에 내담자 이름이 들어가도 로그엔 안 들어간다.
- 임시 변환 파일도 `temp_f07db043.wav` 같은 무작위 이름을 쓴다.
- Electron 권한 처리도 **카메라·마이크·위치정보는 거부**, 클립보드만 허용으로 잠겨 있다
  (`electron-main.cjs:292`).

### 🟡 P1. 딱 두 군데, 파일명이 로그에 남는 경로가 있다 (경미)

**[확인]** 위 원칙에서 벗어난 예외가 두 곳 있다.

1. `server/app.py:1137` — **지원하지 않는 형식의 파일**을 넣었을 때만
   `[오류] 지원하지 않는 파일 형식: .hwp (파일명: 홍길동_3회기.hwp)` 처럼 **파일명 전체**를 로그에 남긴다.

**권장 조치**: 두 곳도 확장자만 남기도록 수정. **다만 서버 파일 수정이라 `app.exe` 재빌드가 필요하니

## 2. 안정성 · 데이터 안전

### 🟠 A1. 자동저장이 실패하면 화면이 통째로 멈출 수 있다 — ✅ 2026-08-06 수정 완료

> **수정 내용**: `gb_autosave_raw` 는 **저장 코드 자체를 제거**했다. 확인해 보니 저장만 하고
> **읽는 곳이 한 군데도 없었다**(최초 커밋부터 그랬다). 예전에 "앱 다시 켜면 이전 작업 복원" 기능이
> 있었는데 이전 상담 내용이 그대로 보이는 문제로 복원만 없애고 저장 코드가 남은 것이다(사용자 확인).
> 아무도 안 쓰는 데이터를 문장마다·타이핑마다 축어록 전체로 다시 쓰고 있었고, 비정상 종료 시
> 상담 내용이 앱 저장공간에 남을 여지도 있었다. 제거로 낭비·위험·프라이버시 문제가 함께 해소됐다.
> `gb_convert_progress`(이어하기 — 실제로 쓰이는 기능)는 유지하되 `try/catch` 로 감쌌다.



**[확인]** `Index.tsx:1014`
```ts
useEffect(() => { if (rawText) localStorage.setItem("gb_autosave_raw", rawText); }, [rawText]);
```
와 `Index.tsx:1405` 의 `gb_convert_progress` 저장에 **오류 처리(try/catch)가 없다.**
브라우저 저장공간(보통 5MB)이 가득 차면 이 코드는 예외를 던지는데, 화면 갱신 도중 터지는 예외라
**변환 중이던 화면 전체가 죽을 수 있다.** (같은 파일 안에서도 분석 이어하기 저장(`836행`)은
`try/catch` 로 감싸 "이어하기만 포기"하도록 처리해 뒀다 — 이쪽만 빠져 있다.)

**[추정]** 실제로 5MB 를 넘으려면 아주 긴 축어록이어야 해서 흔한 일은 아니다. 다만 터지면 피해가
"작업 중이던 변환 화면 사망"이라 크다.

**권장 조치**: 두 곳 다 `try/catch` 로 감싸고, 실패 시 조용히 자동저장만 포기(작업은 계속).

### 🟡 A2. 변환이 길어질수록 자동저장이 무거워진다 (효율) — 🔸 절반 해소

> A1 수정으로 **두 벌 중 한 벌(`gb_autosave_raw`)이 사라져** 부담이 절반으로 줄었다.
> 남은 `gb_convert_progress` 는 여전히 문장마다 전체 텍스트를 다시 쓴다(디바운스 미적용).



**[확인]** `Index.tsx:1405` 는 문장이 하나 나올 때마다 **그때까지의 전체 텍스트를 통째로** 다시 저장한다.
게다가 `gb_autosave_raw` 도 같은 텍스트를 또 저장해서 **같은 내용이 두 벌** 들어간다.
2시간짜리 축어록이면 문장 수백 개 × 매번 전체 텍스트 쓰기라, 뒤로 갈수록 누적 비용이 커진다.

**[추정]** 이번에 겪은 "오래 작업할수록 느려지는 느낌"에 이것도 일부 기여했을 가능성이 있다
(이미 고친 재생 위치 계산 문제와 별개로).

**권장 조치**: 저장을 매 문장이 아니라 몇 초 간격으로 묶어서 하기(디바운스), 중복 저장 한 벌로 정리.

## 2-2. 저장 · 불러오기 (추가 검토)

### 🟢 저장은 튼튼하게 만들어져 있다

**[확인]** `quickSave`(문서 저장) 는 이 정도면 잘 짜여 있다:

- 워드(.docx)와 **세션(.json)을 항상 함께** 저장한다 → 워드가 깨져도 작업을 이어받을 길이 남는다.
- 두 번째 저장부터는 **"이 파일에 저장할까요?" 를 확인**해서 엉뚱한 파일 덮어쓰기를 막는다.
- 저장 중 오류가 나면 **저장 위치 기억을 초기화**해서, 파일을 옮기거나 지웠어도 다시 누르면 복구된다.
- 사용자가 저장 대화상자를 취소한 경우(`AbortError`)와 진짜 실패를 구분해 처리한다.

### 🟡 D1. 세션 파일이 안 열릴 때 이유를 알 수 없다 (경미)

**[확인]** `loadSession` 은 실패 시 `alert("세션 파일을 읽을 수 없습니다.")` 만 띄운다.
가계도 쪽에서 같은 문제로 원인 찾느라 고생한 적이 있다(2026-07-19: 알고 보니 SVG 파일에 확장자만
.json 을 붙인 파일이었음 — 오류 메시지를 보고서야 파악됨).

**권장 조치**: 실제 오류 내용을 함께 보여주기. 한 줄 수정이고 위험이 없다.

### 🔍 D2. 마지막으로 편집한 줄이 저장에 반영되는지 확인 필요 — **[추정]**

**[확인]** 줄 편집 내용은 **포커스가 빠질 때(`onBlur`)** 앱 데이터에 반영된다.
**[추정]** 그렇다면 "마지막 줄을 고치고 곧바로 저장 버튼을 누르는" 흐름에서, 방금 고친 내용이
저장에 반영되기 전에 저장이 실행될 가능성이 이론적으로 있다.

코드만 봐서는 단정할 수 없다(브라우저 이벤트 순서상 대개는 반영되는 게 맞다). **실제 테스트로
확인해야 할 항목**이라 여기 남긴다. 만약 재현되면 저장 직전에 현재 편집 중인 줄을 강제로
반영시키는 처리가 필요하다.

## 3-3. 죽은 코드 정리 (2026-08-06 완료)

TypeScript 컴파일러의 미사용 검사(`--noUnusedLocals --noUnusedParameters`)로 **기계적으로** 뽑아
하나씩 근거를 확인한 뒤 제거했다(추측으로 지우지 않음). win·mac 동일 적용.

| 지운 것 | 근거 |
|---|---|
| `exportTxt`(txt 저장) | **최초 커밋부터** 어떤 버튼에도 연결된 적 없음. 워드 저장이 서식+세션까지 담당 |
| `handleDelete`·`deleting`(변환 모델 삭제) | 2026-07 모델 단일화로 UI 사라짐. 모델이 하나뿐이라 삭제 의미 없음 |
| `MODEL_INFO`(small/medium/large-v3 목록) | 단일화로 선택 UI 자체가 없어짐 |
| `Select*` import | 선택 드롭다운이 사라져 미사용 |
| `modelsState` + `/api/models/status` 호출 | 받아만 두고 안 씀 → **서버 요청 1건 절약** |
| `activeState`, `currentModel`/`onModelChange`/`onEngineChange` props | 위 변경들의 잔재 |

**검증**: 정리 후 `Index.tsx` 기준 미사용 항목 0개, 타입 오류 0개.

> ⚠️ 남은 것: `Genogram.tsx` 에 미사용 항목 9개(쌍둥이 기능 관련 `twinSelectMode`·`twinPending`·
> `twinIdentical` 등). 축어록과 별개 영역이라 가계도 검토 때 함께 판단한다.
> **주의: 쌍둥이 기능이 미완성 상태로 남은 것일 수 있으므로, 지우기 전에 의도를 확인해야 한다.**

## 6. 보류된 아이디어 — 사례서랍에서 한글 문서 보기

사용자 요구: "곤글박이 안에서 파일을 자유자재로 열고 참고하고 싶다".

**[확인] 한글 프로그램 자체를 곤글박이 창 안에 끼워 넣는 것은 불가능하다**(ActiveX 류 임베딩을
Chromium/Electron 이 지원하지 않음). 대안은 두 가지였다.

- **방법 A — 설치된 한글을 자동화해 PDF 로 변환 후 앱 내 PDF 뷰어로 표시**
  서식 완벽, hwp·hwpx 모두 가능. 단 한글 설치 필수 · 한컴 보안 승인창 · 윈도우 전용.
- **방법 B — 직접 변환(olefile[BSD] + zlib 로 hwp 본문 추출)**
  한글 불필요. 단 **글자만** 추출(표·서식 없음), 암호 문서 불가.

**보류 결정(2026-08-06)**: 현재 PDF 뷰어 자체가 보기 불편해서(위 항목), PDF 로 변환해봐야
만족도가 낮다고 판단. **PDF 뷰어 사용성을 먼저 개선한 뒤 재검토**하기로 함.

참고: 지금도 hwp 는 **"시스템 기본 프로그램으로 열기" 버튼으로 한글에서 열 수 있다**(암호 문서 포함).
